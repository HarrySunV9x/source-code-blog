# 分析与证据规范

本文件规定研究应该深入到哪里，以及如何防止主题遗漏。以用户要理解的问题为单位使用，不把每个项目都强制套进全部表格。

## 1. 覆盖与概念依赖

先独立建立两份范围线索，再对照，不要让已有正文决定调查范围：
- 用户方向：明确问题、推导答案所需前提、相邻或易混淆的机制。
- 源码方向：围绕目标检查模块职责、入口与实际执行者、关键状态结构、主要选择或转换规则、失败与释放路径及跨模块交接。由这些证据发现用户没有点名、正文尚未提到的机制；不要求遍历整个仓库。

“必讲机制”是用户明确要求的机制，或缺少它就无法解释目标行为、结果来源、关键边界及相互关系的机制。以读者问题对应的一段因果过程为单位，不把每个函数或变量都作为独立机制。基础前提教到后文能够使用；不影响目标结论的背景只需契约或简述。把某项列为背景或范围外，应能说明它为什么不影响目标推理，而不是因为尚未读懂。

找到公共入口、状态更新或结果计数的位置后，反查主要调用者、分派分支与绕过该位置的处理路径。按实际行为合并等价来源；改变触发条件、执行者、计量或完成方式的来源要分开解释。搜索目标符号只找到共同更新点时，不等于已查清产生结果的所有主要来源。不要求逐一展开所有调用点，但要说明分组依据、适用边界和未确认范围。

在已有工作笔记中按必讲路径分别记录：为什么需要讲、源码证据、正文位置、当前缺口。可以使用下表，也可以用同等明确的简短记录；不要为每个变量建表。

| 路径或机制 | 源码证据 | 正文位置 | 当前情况与下一步 |
|---|---|---|---|
| 来源甲 | 已找到入口与执行分支 | 某节 | 已解释过程，待核验变条件结果 |
| 来源乙 | 仅找到公共函数调用 | 只有一句提及 | 未完成：继续查触发与交接 |

没有证据或只有名称不能标为已讲清；不能把多条完成程度不同的路径统一写成“已定位、已推导、已通过”。范围外项目需说明为何不影响用户所问的结果；“不确定运行时是否启用”应写成适用条件，不能单凭此理由跳过可获得的实现。无需展开不影响主题结论的子系统细节。

不要把同一事物的不同观察角度当成互斥分类。例如底层存储、分配方式、持有者和用途可能描述同一对象；队列中的任务、运行状态记录和调用者持有的结果句柄也可能关联同一次工作。查清它们的真实关系，而非因名字相似就合并，或因名字不同就相加。

## 2. 追踪数据：读取方向与更新方向都要走

针对决定核心结论的值，回答以下适用问题：

| 要回答什么 | 应找的证据 |
|---|---|
| 这个值属于谁？ | 类型定义、实际实例、生命周期；临时输出字段与长期状态分开 |
| 最初从哪里来？ | 初始化、分配、输入接收或查询；不要停在一次赋值 |
| 谁因为什么事件改它？ | 写入、加减、状态转换的调用位置与前置条件 |
| 一次操作改多少？ | 更新表达式、单位、批量因子、成功与失败分支 |
| 相反操作怎样处理？ | 撤销、移除、释放、回滚、重试及不对称之处 |
| 谁使用这个值？ | 读取路径、派生计算、分支决策、输出换算 |
| 为什么可能与另一处不同？ | 范围、对象、时间、共享、聚合、缓存、近似或配置差异 |

形成双向闭环：

```text
读侧：用户看到的结果 ← 换算或派生值 ← 中间字段 ← 实际状态
写侧：真实事件 → 条件判断 → 状态更新 → 汇总或传播 → 读侧可见
```

用户问“受什么影响”时，追踪不能止于加数语句。对主要因素说明：改变了什么输入或状态、哪个条件因此选择不同处理、谁实际执行、结果在何处变化。参数文档只能说明配置含义，不能替代这些执行证据。若因素只改变时机而不必改变总量，或只有特定路径受影响，应明确区分。

重要统计还需查明：统计对象与计量单位、全局/进程/线程/对象等范围、去重与分摊方式、瞬时读取或缓存值、更新延迟、一致性，以及重置条件。不要预设所有字段来自同一种统计机制。展示公式时说明成立条件，尤其是多个输出并非同一时刻采样时。

查询到 `result.value = get_value()` 只找到传递关系；找到 `COUNTER_X` 只找到分类；还应找到计数的实际存储、增减事件和读取语义。若本次问题依赖聚合细节，继续追踪聚合更新，不能把“全局”误说成每次读取时遍历所有对象求和。

对于不可获得的实现，列出缺失位置及其影响；可以解释已验证的契约，不能靠命名补齐内部行为。

## 3. 统一的机制完成标准

对每个必讲机制使用以下适用维度。它们是调查和验收标准，不是强制文章小标题；确实不适用的维度可以略去，但不能用“不适用”掩盖未调查。统计、算法、协议、资源管理等都按同一标准判断完成程度，上一节的数据追踪是其中一种具体应用。

| 维度 | 正文应使读者能够回答 |
|---|---|
| 状态表示 | 处理的真实对象是什么？关键结构和字段如何表示对象、关系及当前状态？为什么某状态允许下一步操作？ |
| 操作规则 | 给定输入和初始状态，如何查找、选择、计算或转换？哪些条件决定分支、循环推进和停止？中间状态如何到达结果？ |
| 成立条件 | 过程依赖哪些前提或不变量？关键操作怎样保持它们，何时可能失效？用实现说明成立原因，不臆测作者动机。 |
| 边界路径 | 哪些失败、容量或状态边界会改变结果？如何回退、等待、重试或终止？部分完成后留下什么？ |
| 并发与可见性 | 若有并发，谁竞争什么状态，什么保护覆盖哪些操作？更新何时对谁可见，锁外或异步阶段依赖什么条件？ |
| 生命周期与关系 | 谁产生、消费、持有、转移、撤销和释放？相邻机制或接口怎样观察或改变同一对象？ |
| 推导能力 | 改变一个相关输入、初始状态或操作顺序，读者能否仅凭正文推导不同结果并指出依据？ |

### 算法不能止于调用关系或最终写入

找到选择器、转换函数或状态更新语句后，继续解释它使用的表示方式与决策规则。例如搜索或调度要说明候选集合、顺序或优先级、选中条件、找不到时的路径；拆分或合并要说明结构如何变化、匹配方式及允许或禁止操作的条件；反馈算法要说明信号何时产生、如何改变后续选择。这些是按实际机制选用的调查方向，不要求每个项目都涵盖这些算法。

给出符合代码的具体初始状态，逐步推导一次操作；再改变会触发不同分支的条件。只有入口、分派器、统计增量或“调用某函数完成处理”的文字，无法证明算法已经讲清。关键规则位于帮助函数内时，必须解释该规则，不能用一个源码链接代替。

### 生命周期与并发要解释约束

异步操作从提交追到真正的消费者和结果传回路径。区分已提交、已接收、已开始、已完成、结果可见；核对取消、超时与实际工作结束是否一致。

资源和引用分别追踪：引用减少、访问撤销、逻辑删除和底层释放可能是不同事件。失败时核对已取得的资源以及补偿操作；不把成功路径自动套到回滚路径。

发现锁、原子操作或引用计数后，解释其保护对象、范围及保证。仅说“加锁保证线程安全”不足以说明并发机制；要检查依赖该保证的读写和交接是否位于保护范围内。无需穷举所有线程排列，选择会影响目标结论的竞争场景。

### 何时可以停止追踪

当上述适用问题都有证据、关键条件改变时仍能推导行为，并且正文给出了所需前提与操作规则，才算该机制解释完成。源码事实已找到但尚未写清时，应继续写作；推导不了时应继续调查。不能用固定调用层数、函数名、字段赋值或进入依赖库作为停止标准。

若目标只依赖外部输入输出契约且不涉及内部机制，验证契约后可停止；若内部机制正是用户要理解的内容，契约不能替代实现。实现确实不可访问时指出缺失位置、影响哪些结论及已验证的边界，保留未完成状态；未继续阅读本地可用代码不属于证据不可得。

## 4. 对齐多个观察角度

对于相邻或易混淆的概念，先分别完成来源追踪，再建立关系。可以比较对象、数据来源、更新事件、统计范围、单位、时间和共享关系，不要求每次都输出大表。

用同一对象经历一连串操作验证关系：创建但未使用、由一个主体使用、被另一个主体共享、一个主体退出、最后解除持有或释放。选择符合代码的步骤，不强套这个顺序。记录各步骤下每个观察者看到的变化，并把变化对应到代码。

这种验证能发现：同一对象被多次统计、逻辑资源与实际存储混淆、撤销访问误当释放资源，以及两个名称相近的数值来自不同事件。场景推不出来时继续研究，不能用“通常如此”绕过矛盾。

## 5. 证据与解释的边界

源码位置有效，不代表支持该结论。对照结论中的动词和限定词检查证据：代码能否证明“分配”“共享”“一定”“立即”“所有”等表述？默认配置是否被误写为普遍行为？注释表达的意图是否与实现一致？

设计理由应区分明示证据与推断；“这样做可以减少某种成本”不等于作者明确为了该目的设计。数字场景说明页大小、并发、共享次数等影响结果的假设，不把示意值写成测量结果。

## 6. 验证本 skill 的泛化能力

修改 skill 时，先检查是否把某次反馈转成了适用于同类遗漏的完成标准，再检查其他机制会不会仍被放过。不要把用户举出的符号或文章章节写成必选分析目录。

需要行为验证时，选不同类型的真实代码做小范围试作：
- 选择或转换算法：读者能推导候选、执行步骤、边界与停止；仅有分派调用或最终赋值应判为不足。
- 统计接口：从输出追到真实更新，并比较同一事件在不同接口中的结果；只解释中间字段应判为不足。
- 异步或跨模块资源：追到执行、结果可见及失败或取消后的持有关系；只列回调或锁名应判为不足。

试作至少涉及本次反馈未点名的机制。检查实际产物是否解释了必要因果，而不是标题、关键词或引用数量是否齐全。独立试用若可用且已获授权，只提供真实请求、skill 和所需原始代码，不提供预期答案、已知漏洞或修复结论。

区分结构检查、人工规则审查、真实代码试作与独立试用。未执行的验证不能写成通过；自查不能证明泛化效果。不要因验证而默认启动未获授权的子代理，或扩展用户任务。发现缺口后修正共性的决策规则，避免持续堆积针对单个例子的禁令。
